# Трассировка и покрытие

## Модель

```text
BR → SR → FR / NFR
CON ──── ограничивает ─→ BR / SR / FR / NFR / решение
TR ───── обеспечивает ─→ изменение / целевое состояние
тест / критерий приёмки ── проверяет ─→ FR / NFR
```

Пропуск уровня допустим (например, системное NFR распространяется на решение
целиком), если сохранено бизнес-основание. Не требуй искусственного
прохождения через каждый уровень, но любой пропуск объясняй.

## Связи

Используй понятные глаголы: `обосновывает`, `реализует`, `уточняет`,
`ограничивает`, `зависит от`, `проверяется`, `конфликтует с`, `заменяет`.

Статус связи:

- `Подтверждено источником` — смысл исходного обязательства обосновывает обе записи и связь между ними. Приведи точную цитату. Источнику достаточно описывать потребность и поведение обычным языком. Например, из «По вкладу клиента ежедневно начисляются проценты» следуют потребность клиента в ежедневном начислении и функция начисления по вкладу. Их связь сохраняй в дереве. Само разложение на SR и FR не создаёт вопроса.
- `Предполагается` — чтобы обосновать связь, приходится добавить бизнес-допущение. Назови решение, которое зависит от владельца. Если источник обещает показать начисления, выбор выписки как обязательного канала требует согласования. Предложенный канал занеси в гипотезы, открытый выбор — в GAP с затронутыми ID и вопросом «Где клиент должен видеть начисления?». Если обе записи уже подтверждены по отдельности, сохрани предполагаемую связь и укажи в GAP, что именно нужно решить.

Близость фраз, общий раздел или правдоподобная причинность не делают связь
подтверждённой. Формулировка «каждый сценарий способствует бизнес-результату»
остаётся предположением, если источник подтверждает только вклад решения
в целом.

## Проверка покрытия

Цель — каждая `BR` и `SR` доведена декомпозицией до `FR`/`NFR`: по составу
требований должно быть понятно, как реализовывать потребности. После
построения связей проверь:

- `BR` без дочерних `SR` и `SR` без `BR` (структурные сироты);
- `SR` без `FR`/`NFR`: потребность не декомпозирована до реализуемого поведения — `GAP`, а не молчание;
- `FR`/`NFR` без родительской потребности;
- `CON`, не ограничивающие ни один элемент;
- зонтичную способность: пока состав обобщающего термина не подтверждён
  как исчерпывающий, её покрытие частичное, даже если все названные дети
  существуют;
- `NFR` без области действия.

Не создавай недостающие элементы автоматически ради красивого покрытия:
показывай разрыв и `GAP`.

## Формат вывода

Сначала выведи фактическую иерархию в виде компактного дерева: ID и короткое
имя каждого элемента, прямые связи `SR → FR`, пометки о частичном покрытии,
отсутствующих `NFR` и ограничивающих `CON`. Дерево — карта логики
`BR → SR → FR/NFR`: по ней сразу видно, где цепочка рвётся.

Затем таблицей — только связи, которые в дерево не помещаются: конфликты,
зависимости, замены и связи со статусом `Предполагается`, требующие
пояснения. Если таких нет — одна итоговая строка. Полную построчную матрицу
выводи только по запросу пользователя.
