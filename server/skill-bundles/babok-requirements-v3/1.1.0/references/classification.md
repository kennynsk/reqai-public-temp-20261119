# Классификация и правила доказательности

## Типы элементов

| Код | Что это | Ключевой вопрос |
|---|---|---|
| `BR` | Один самостоятельно желаемый бизнес-результат | «Зачем организации изменение?» |
| `SR` | Одна независимо согласуемая потребность роли с наблюдаемым результатом | «Что нужно конкретной роли?» |
| `FR` | Одно наблюдаемое действие решения: условие, действие, объект, результат | «Что делает решение?» |
| `NFR` | Проверяемое качество решения с областью действия и правилом | «С каким качеством?» |
| `TR` | Временное действие перехода с критерием завершения | «Что нужно только на время перехода?» |
| `CON` | Обязательное ограничение: закон, договор, стандарт, политика | «Что обязательно соблюдать?» |

`CTX`, `GAP`, `HYP`, `TERM` — служебные записи реестра (контекст, пробелы,
гипотезы, термины), а не типы требований. Не принуждай контекст, факты,
бизнес-правила, риски и дизайн-решения к одному из шести типов.

`BR` описывает результат, а не функцию, канал или роль банка. `SR` не описывает
внутреннее поведение системы. `TR` нужен только для перехода: миграция,
обучение, параллельная работа, временный интерфейс.

## Правила доказательности

Определяй роль утверждения по смыслу, а не по заголовку раздела.

| Фрагмент источника | Куда попадает |
|---|---|
| Проблема, риск, возможность, выгода | `BR`; потребность роли, названная в проблеме, — `GAP` о включении в scope, если раздел решения её не подтверждает |
| Обязательство решения, названный сценарий | `SR` и/или `FR` |
| Закон, договор, стандарт, политика | `CON`; конкретные `FR`/`NFR` — только из подтверждённых положений |
| Качество решения без области и проверяемого правила | `GAP` или вопрос, не готовый `NFR` |
| Текущее состояние, состоявшийся факт | `CTX`; не `TR` и не delta |
| Предпочтение реализации | `CTX`; `CON` — только при подтверждённой обязательности |
| Правдоподобная, но не названная функция | `HYP`, не требование |

Ключевые запреты:

- Фрагмент о проблеме или выгоде не подтверждает `FR`. Если потребность
  подтверждена, а включение функции в решение — нет, зафиксируй `GAP` с
  вопросом о включении в scope, но не выдуманный `FR`.
- `CON` не удаляется из реестра из-за отсутствия документа, пункта или
  метрики: сохрани ограничение не конкретнее источника и зафиксируй пробел.
- `TR` создаётся только из будущего временного действия с критерием
  завершения. Состоявшийся факт текущего состояния — `CTX`.

## Неподтверждённый scope

Потребность роли, названная в проблеме или выгоде, но не перечисленная в
разделе решения, не становится подтверждённым `FR`. Зафиксируй её одним
`GAP` («не решено, входит ли в scope») со ссылкой на `BR` и вопросом
владельцу. После подтверждения потребность переносится в реестр как
`SR`/`FR`; после отказа фиксируется как явно исключённая.

## Обязательные ограничения (CON)

Для `CON` фиксируй обязательство, источник (закон, договор, стандарт,
политика), известные реквизиты (версия, пункт, дата) и область применения.
Отсутствующие реквизиты, владелец контроля и метод доказательства связывай
с `GAP`, не заменяя их выдуманными значениями.

## Идентификаторы

Используй `BR-001`, `SR-001`, `FR-001`, `NFR-001`, `TR-001`, `CON-001`,
`CTX-001`, `GAP-001`, `HYP-001`, `TERM-001`, `DELTA-001`
с отдельной нумерацией по типу.
