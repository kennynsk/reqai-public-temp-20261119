# Выявление пробелов и вопросы

Сначала выполни доступную декомпозицию, затем задай вопросы. Вопросы не
блокируют анализ: выдавай отчёт с вопросами, а не жди ответов. Интерактивный
раунд уточнения проводи по запросу пользователя.

## Правила

- 3–7 вопросов за итерацию; если существенных решений меньше, не дополняй
  список формальными вопросами.
- Один вопрос — одно решение; ответ должен менять состав, статус или границу
  требования.
- Привязывай вопрос к `GAP-ID` и ID затронутого требования; укажи вероятного
  адресата (владелец продукта/бизнеса, процесса, архитектуры, ИБ/комплаенс,
  эксплуатация, юридический).
- Не спрашивай о том, что можно извлечь из источника.
- Не предлагай пороги, роли и правила как факты; полезный ориентир — только
  как вариант для согласования.

## Порядок тем

1. Потребность и scope: включать ли требования, названные в проблеме или
   выгоде, но не подтверждённые решением; исчерпывает ли перечисление
   сценариев обобщающий термин; полнота BR — ценность, клиент, роли,
   жизненный цикл.
2. Обязательства: применимые пункты законов, стандартов и договоров, область
   и владелец контроля.
3. Граница и ответственность: кто исполняет сценарии, где источник истины,
   что делает каждая система.
4. Поведение: роли, объекты, состояния, триггеры, правила, исключения.
5. Качества и приёмка: применимые НФТ-категории, метрики, доказательства.
6. Переход: as-is, целевое состояние, миграция, критерии завершения.

## Функциональный проход

Для каждого `SR`/`FR` со статусом `Требует уточнения` проверь: кто
инициирует действие; триггер и предусловия; входные данные; состояния до и
после; основное действие; альтернативы, ошибки и повтор; права роли;
бизнес-правила; затрагиваемые системы и источник истины. Поднимай только
критимые пробелы, не разрастайся в анкету.

Вопросы о формулах, единицах, точности и округлении задавай только для
реально подтверждённой функции расчёта, преобразования или классификации.

## НФТ-проход

Если источник не содержит НФТ, проверь применимость категорий — по риску,
критичности, регулированию, каналу и интеграциям, а не механически:

| Категория | Что уточнить |
|---|---|
| Производительность | Операция, предел времени, нагрузка, объём данных |
| Доступность | Сервисные часы, процент, окно измерения, исключения |
| Надёжность/восстановление | Поведение при отказе, повтор/идемпотентность, RTO/RPO |
| Безопасность | Аутентификация, авторизация, подтверждение операции, аудит |
| Соответствие | Точный норматив, версия, пункты, доказательство |
| Приватность | Состав персональных данных, цели, хранение, согласия |
| Интеграция | Системы, протоколы, форматы, таймауты, обработка ошибок |
| Удобство/доступность | Критичные задачи, аудитория, доля успеха, стандарт доступности |
| Масштабируемость | Число пользователей, рост, пиковый профиль |
| Наблюдаемость | Логи, метрики, трассировка, алерты, срок хранения |

Для регулируемого финансового решения минимум проверь безопасность,
соответствие, доступность, производительность, интеграцию и восстановление.

## Создание NFR

Создавай `NFR` только при известных области действия, проверяемом правиле
или показателе, целевом условии и методе проверки. До этого — `GAP` или
`HYP`; числовые пороги не назначай.
