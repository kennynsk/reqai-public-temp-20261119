Представление качества в JSON-контракте: quality — точное значение перечисления («Готово», «Требует уточнения», «Конфликтует», «Не тестируемо»), без добавления «(GAP-...)» внутрь этого поля. Ссылка на пробел хранится структурно: requirement.relatedIds содержит GAP-ID ИЛИ существующий analysis.GAP перечисляет requirement.id в affectedIds. Оба способа допустимы; отображение собирает их в отчёте. Не объявляй отсутствие ссылки только потому, что в строке quality нет скобок или в relatedIds нет ID, если analysis.GAP.affectedIds уже связывает запись. Сверь весь registryAnalysis. Общий пробел НФТ сам по себе не делает отдельную ясную FR «Требует уточнения»: готовность FR оценивается по её действию и границе, неизвестные качества относятся к НФТ-проходу. Не требуй способа UI-реализации для готовой функции принятия согласия, если роль, объект, действие и результат уже определены.

Независимо проверь каждого кандидата по BABOK. Не переписывай реестр. Верни компактный JSON:
{"schemaVersion":"babok-semantic.v2","revision":"{{revision}}","checks":[{"key":"точный key","classification":"BR|SR|FR|NFR|TR|CON|METRIC|CTX|GAP|HYP","obligations":["краткое действие и объект"],"evidence":"SUPPORTED|PROPOSED|UNSUPPORTED","verifiable":true,"preservesOriginal":true,"distinctOutcome":true,"issues":[],"reason":"","repair":""}],"coverageIssues":[]}
Для каждого key ровно одна checks-запись. obligations — все независимо согласуемые результаты, по 2–6 слов каждый. У корректной атомарной записи ровно один элемент. Не копируй длинный text. У корректных записей reason/repair пустые; у нарушения кратко объясни причину и исправление (до 30 слов). Все boolean-поля обязательны. revision скопируй точно.
BR — самостоятельно желаемый бизнес-результат, не метрика или способ измерения. «Достижение цели измеряется долей...» — METRIC, distinctOutcome=false; показатель уточняет successIndicator исходного BR. Существующий BR с новым показателем и прежним text остаётся BR. Действие решения по расчёту — FR.
SR — одна потребность конкретной роли. FR — одно действие с одним результатом; поля одной записи — один объект, условие/триггер — не отдельное действие. Фиксация подтверждения и перечисление, уведомление и смена состояния, показ и подтверждение получателя — независимые обязательства.
NFR — проверяемое качество; тест должен проверять всю область. Резервирование и перечисление с разными эффектами требуют отдельных правил/тестов. Регистрация событий — FR. TR — только временный переход. CON — подтверждённое обязательное ограничение; отсутствие реквизитов сохраняется GAP, не удаляет CON.
В DECOMPOSITION evidence=SUPPORTED: смысл прямо следует из первичного материала или справочника, не из конфликтующего baseline. В RESEARCH допустим PROPOSED, но новые решения явно остаются гипотезами. Для CON всегда требуется подтверждённое обязательство.
replace сохраняет каждое исходное условие, триггер и результат. Метрика не создаёт вторую цель. Не требуй деталей следующего уровня от BR/SR; неизвестный механизм подтверждённого сценария допускается с GAP, а не выдумывается.
Сверь relatedTo и source: предполагаемую связь с бизнес-целью нельзя выдавать подтверждённой. Проверь покрытие явно названных действий первичного материала и сохранённых ответов. Если обязательство пропало, укажи его в coverageIssues; не требуй реализации гипотез из baseline или справочных описаний. Каждое нарушение в issues, а не в свободном тексте.

Дополнительно проверь каждый фрагмент первичного источника, включая ВСЕ условия, триггеры и результаты. Добавь в JSON sourceRevision из sourceCoverage.revision и sourceChecks:[{"key":"точный SOURCE-key","targetKeys":["ID подтверждённых записей"],"preservesConditions":true,"issues":[],"reason":""}]. Ровно одна проверка на каждый фрагмент. targetKeys только из sourceCoverage.targets. Одной тематической ссылки недостаточно: сопоставь все условия с текстом целевых записей. Исходное резервирование ДО выполнения условий нельзя считать покрытым одним фактом создания резерва. Удаление ошибочного CON не позволяет потерять подтверждённое поведение: сохрани его как условие FR или бизнес-правило CTX; гипотеза о договорной обязательности это поведение не заменяет. Для контекста допустим CTX, но HYP/GAP/TERM не заменяют явное обязательство исходного описания.

Baseline — предыдущая версия для сравнения, не источник, отменяющий первичное описание задачи. Подтверждённое первичным источником изменение не является неподтверждённым scope из-за расхождения с baseline. Если противоречие уже отражено в delta/GAP, оно не требует менять подтверждённое поведение обратно на baseline. При необходимости уточни статус, сохрани первичное обязательство.

Создание сервиса и описание его устройства — scope/CTX, не самостоятельная бизнес-цель BR. «Обеспечить расчёты, при которых деньги резервируются до исполнения условий» описывает решение, а не зачем оно организации: не создавай из этой фразы BR. Самостоятельный BR формулирует желаемый результат организации, например привлечение новых клиентов. Подтверждённое устройство сервиса остаётся SR/FR/CTX с исходными условиями. Не заменяй отсутствующий бизнес-результат названием сервиса или функцией; зафиксируй GAP при его отсутствии.
