Правила глобальной консолидации:

1. Считай все переданные единицы одним источником требований. Не ограничивай
   результат последней единицей и не выдавай массив независимых отчётов.
2. Сохрани только подтверждённые источником BR, SR, FR, NFR, TR и CON.
   Контекст, GAP, HYP и TERM храни отдельно; гипотезы и неподтверждённый
   scope не превращай в требования.
3. Удали семантические дубликаты, даже если формулировки отличаются только
   нормализацией или одна единица повторяет другую. Сохрани наиболее полную
   доказательную цитату и перенеси связи на оставшуюся запись.
4. Назначь глобально уникальные стабильные ID с отдельной нумерацией по типу:
   BR-001, SR-001, FR-001, NFR-001, TR-001, CON-001, CTX-001, GAP-001,
   HYP-001, TERM-001, DELTA-001. Не оставляй коллизии ID от отдельных единиц.
5. Все source должны сохранять artifactId и locator из исходных единиц;
   section evidence не удаляй. Если исходная единица не содержит доказательства,
   создай GAP, а не подставляй правдоподобную цитату.
6. Перестрой traceability на глобальные ID и оставь только существующие
   записи. Каждый link должен иметь непустые from, to и relation и допустимый
   status; неполный link исключи. Явные связи пометь «Подтверждено источником»,
   аналитические — «Предполагается». Проверь покрытие BR → SR → FR/NFR и
   покажи разрывы через GAP.
7. Сравнивай с baseline только при его статусе AVAILABLE. Без baseline delta
   должен быть пустым и нужно явно сообщить, что сравнение невозможно. Для
   UNAVAILABLE создай GAP о недоступном материале и не создавай delta.
8. Не назначай роли, системы, объекты, правила, числовые пороги или ответственность,
   которых нет в материалах. Создавай CON только при наличии подтвержденного
   непустого obligation; не оставляй CON-заполнители с пустым обязательством,
   а фиксируй неподтвержденный пробел через GAP. Для конфликтов, неполного
   scope и частичного выполнения оставь отдельные записи анализа.
9. Объедини вопросы, оставь 3–7 приоритетных вопросов, каждый с gapId,
   addressee, priority P0/P1/P2 и формулировкой одного решения.
10. outcome должен быть PARTIAL, если часть единиц не обработана или остались
    ошибки охвата; COMPLETE — только при полном охвате доступных единиц.

Верни полный JSON-контракт:

{
  "schemaVersion": "babok-requirements.v1",
  "mode": "DECOMPOSITION",
  "outcome": "COMPLETE",
  "summary": {"text": "...", "counts": {"BR": 0, "SR": 0, "FR": 0, "NFR": 0, "TR": 0, "CON": 0, "CTX": 0, "GAP": 0, "HYP": 0, "TERM": 0, "DELTA": 0}, "conclusions": []},
  "context": [],
  "groups": {"BR": [], "SR": [], "FR": [], "NFR": [], "TR": [], "CON": []},
  "analysis": {"GAP": [], "HYP": [], "TERM": [], "traceability": [], "delta": [], "questions": []},
  "materials": {"primary": null, "baseline": {"status": "NOT_PROVIDED", "artifacts": []}, "references": []},
  "scope": {"partial": false, "units": []}
}

Все массивы обязательны. У requirements должны быть source, provenance, quality
и связи своего типа; source имеет artifactId, locator, quote. Ссылки должны
разрешаться в объединённом результате. Счётчики summary.counts должны точно
совпадать с длинами массивов. Не включай служебные рассуждения вне JSON.
