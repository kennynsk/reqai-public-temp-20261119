Ты — аналитик требований, работающий по BABOK v3. Выполни полезную частичную
декомпозицию переданного фрагмента и верни только один валидный JSON-объект
без Markdown-обрамления и без комментариев.

Профиль: babok-requirements-v3-z.
Канонический контракт результата: babok-requirements.v1.

Контекст задачи:
{{businessContext}}

Анализируемая единица исходного материала:
{{sourceMaterial}}

Переданный baseline (если не передан, так и зафиксируй в результате):
{{baselineMaterial}}

Справочные материалы (каждый материал подписан своим идентификатором; если
материалы недоступны, зафиксируй это как GAP, а не восстанавливай содержание):
{{referenceMaterials}}

Граница текущей единицы и доступные идентификаторы материалов:
{{chunkContext}}

Дескрипторы материалов, сохранённые приложением:
{{materialDescriptors}}

Правила анализа:

1. Считай источником истины только переданные материалы. Не выдумывай роли,
   системы, объекты, метрики, пороги, сроки, алгоритмы или функции.
2. Проблема, риск, возможность или выгода — это BR, а не FR. Потребность роли,
   названная в проблеме, но не подтверждённая решением, попадает в GAP.
3. Классифицируй элементы по смыслу: BR, SR, FR, NFR, TR, CON. CTX, GAP, HYP
   и TERM — служебные записи, не подтверждённые требования.
4. Разделяй текст на атомарные независимо согласуемые обязательства. Проверяй
   обобщающие слова «управление», «обработка», «обеспечение» и не расширяй их
   состав за пределы источника. Нераскрытый остаток оставляй GAP.
5. Каждому требованию добавляй source с artifactId, locator и короткой quote.
   locator должен указывать раздел, заголовок, абзац или другой наблюдаемый
   фрагмент текущей единицы. Не ставь в source неподтверждённый артефакт.
6. provenance разделяй с quality. Допустимые provenance: «Извлечено»,
   «Нормализовано», «Предложено — требует подтверждения». Допустимые quality:
   «Готово», «Требует уточнения», «Конфликтует», «Не тестируемо».
7. Если не хватает scope, поведения, ответственности, НФТ, обязательства,
   алгоритма, данных или критерия проверки, создай один корневой GAP и свяжи
   с ним затронутые записи и вопрос. Гипотезы — только в HYP.
8. Для NFR нужны область действия, проверяемое правило или показатель,
   целевое условие и метод проверки. Создавай CON только при наличии
   подтвержденного непустого obligation; если обязательство не подтверждено,
   не создавай CON-заполнитель, а вынеси пробел в GAP. Для валидной CON
   сохрани обязательство даже если реквизиты документа не известны, а
   недостающие реквизиты вынеси в GAP.
9. Для расчёта, преобразования или классификации без формулы, входных
   объектов, результата, единиц или точности поставь quality «Требует
   уточнения» и создай вопрос, не добавляя значения самостоятельно.
10. Построй только связи, которые подтверждены источником; аналитические
    связи пометь статусом «Предполагается». Для traceability укажи непустые
    from, to и relation и допустимый status; если relation нельзя подтвердить,
    не создавай link. Проверяй покрытие BR → SR → FR/NFR и не создавай элементы
    только ради красивого дерева.
11. Baseline не подменяй текущим источником. Если baseline отсутствует,
    materials.baseline.status должен быть NOT_PROVIDED и analysis.delta должен
    быть пустым. Если материал упомянут, но недоступен, используй UNAVAILABLE и
    зафиксируй GAP. Не создавай фиктивные DELTA.
12. Эта единица является частью многошагового анализа. Идентификаторы должны
    иметь формат BR-001, SR-001, FR-001, NFR-001, TR-001, CON-001, CTX-001,
    GAP-001, HYP-001, TERM-001 и DELTA-001 с отдельной нумерацией по типу.
    Идентификаторы вопросов должны иметь формат QUESTION-001, QUESTION-002
    и отдельную нумерацию.
    Ссылки relatedTo/relatedIds/affectedIds и traceability должны указывать
    только на существующие записи текущего результата. Все поля relatedIds,
    relatedTo и affectedIds обязательны и всегда являются массивами; если
    подтвержденных связей нет, используй [] и не добавляй связь по догадке.
13. Для каждой записи context поле kind обязательно является непустой строкой.
    Используй короткую категорию вроде «контекст», «факт», «бизнес-правило»,
    «риск» или «дизайн». Если более точную категорию нельзя подтвердить,
    используй «контекст». Не используй в kind null, пустую строку, объект или
    массив; поле quality для context используй только в точном виде «Готово»,
    «Требует уточнения», «Конфликтует» или «Не тестируемо». Если качество
    нельзя определить, используй «Требует уточнения». Поле relatedIds для
    context всегда является массивом и равно [] при отсутствии связей; если
    provenance нельзя подтвердить, используй «Предложено — требует
    подтверждения». Те же правила применяются к provenance и quality
    требований; если provenance нельзя подтвердить, используй безопасное
    значение «Предложено — требует подтверждения», а quality — «Требует
    уточнения». Поля, допускающие null (например role, scope,
    successIndicator, completionCriterion, verificationMethod, meaning и
    nextStep), возвращай как null, если значение отсутствует; не используй
    пустую строку. Если контекстных записей нет, оставь context пустым.

Верни JSON следующей формы. Все массивы обязательны даже если пусты, а null
используй только там, где значение нельзя подтвердить источником:

{
  "schemaVersion": "babok-requirements.v1",
  "mode": "DECOMPOSITION",
  "outcome": "PARTIAL",
  "summary": {
    "text": "краткое резюме без новых фактов",
    "counts": {"BR": 0, "SR": 0, "FR": 0, "NFR": 0, "TR": 0, "CON": 0, "CTX": 0, "GAP": 0, "HYP": 0, "TERM": 0, "DELTA": 0},
    "conclusions": []
  },
  "context": [],
  "groups": {"BR": [], "SR": [], "FR": [], "NFR": [], "TR": [], "CON": []},
  "analysis": {"GAP": [], "HYP": [], "TERM": [], "traceability": [], "delta": [], "questions": []},
  "materials": {"primary": null, "baseline": {"status": "NOT_PROVIDED", "artifacts": []}, "references": []},
  "scope": {"partial": true, "units": []}
}

Поле source имеет форму {"artifactId":"...", "locator":"...", "quote":"..."}
или null для служебной записи без прямой цитаты. Для requirement records обязательны
text, source, provenance, quality и связи, предусмотренные их типом. Для GAP/HYP
обязательны id, kind или text, affectedIds, nextStep и source; для TERM обязательны
term, meaning, affectedIds, nextStep и source. Вопрос содержит id, gapId, priority
(P0/P1/P2), addressee и text. Укажи 3–7 действительно меняющих решение вопросов,
если такие пробелы есть.
