Подтверждённое требование может быть неполным: это допустимый аналитический результат, не ошибка классификации или scope. Для FR/TR с неизвестным механизмом, алгоритмом, форматом либо критерием завершения сохраняй явное обязательство, quality="Требует уточнения" и конкретный связанный GAP. Не выдумывай недостающие решения ради прохождения проверки. TR без completionCriterion допускается только в этом статусе со связанным GAP; у "Готово" критерий обязателен. Не записывай MECHANISM_UNDEFINED / COMPLETION_CRITERIA_INCOMPLETE в issues, если неизвестное уже честно отражено статусом и конкретным GAP. verifiable может быть false для такого FR/TR; это оценка готовности, не основание отклонять весь реестр. Реальные ошибки типа, атомарности, выдуманные факты и потеря исходных условий по-прежнему исправляй.
Компания/роль, которой нужны загрузка, проверка и отправка реестра, имеет три независимо согласуемые потребности SR; не объединяй их в одну. Одна роль не делает разные действия атомарными. Лимиты объёма и условия частичного исполнения сохраняй при разделении.

Приоритетный список analysis.questions содержит 3–7 вопросов. Все пробелы остаются в analysis.GAP, даже если не попали в семь приоритетных вопросов. Если исправление добавляет GAP, добавлять восьмой QUESTION нельзя: выбирай важнейшие P0/P1/P2. Нарушение BABOK_PRIORITY_QUESTION_LIMIT с точным QUESTION-ID разрешает убрать только этот вопрос через removeIds, сохранив GAP и обязательства. До ответа проверь каждую BR/SR: у неё есть дочерняя FR/NFR или конкретный GAP, включающий её ID в affectedIds.

Представление качества в JSON-контракте: quality — точное значение перечисления («Готово», «Требует уточнения», «Конфликтует», «Не тестируемо»), без добавления «(GAP-...)» внутрь этого поля. Ссылка на пробел хранится структурно: requirement.relatedIds содержит GAP-ID ИЛИ существующий analysis.GAP перечисляет requirement.id в affectedIds. Оба способа допустимы; отображение собирает их в отчёте. Не объявляй отсутствие ссылки только потому, что в строке quality нет скобок или в relatedIds нет ID, если analysis.GAP.affectedIds уже связывает запись. Сверь весь registryAnalysis. Общий пробел НФТ сам по себе не делает отдельную ясную FR «Требует уточнения»: готовность FR оценивается по её действию и границе, неизвестные качества относятся к НФТ-проходу. Не требуй способа UI-реализации для готовой функции принятия согласия, если роль, объект, действие и результат уже определены.

Выполни рабочий процесс скилла для анализируемой единицы. Полный источник приложен для проверки scope и связей между разделами. Извлекай требования из текущей единицы; не считай отсутствие сведений в ней отсутствием сведений во всём источнике. Это предварительный анализ перед глобальной проверкой.

Ответ компактным JSON без отступов. Формулировки краткие, без повторения обоснований в каждой ячейке. Одна бизнес-цель — один BR; способ измерения — его successIndicator, не новый BR. Если источник называет отмену, истечение срока, спор или неответ, раздели их независимые сценарии; не добавляй отсутствующие в источнике. Не объединяй их в зонтичный SR. Триггер и ограничение одного действия не являются вторым обязательством. У неподтверждённых связей статус «Предполагается», не дублируй их в relatedTo/relatedIds. Короткие точные непрерывные цитаты, без многоточия. Не создавай функции из вероятного поведения.

Для единственной единицы источника это готовый кандидат финального реестра: выполни проверки GAP и трассировки уже сейчас. У каждой строки «Требует уточнения» должен существовать конкретный GAP с этим ID в affectedIds, включая неизвестный способ подтверждения исполнения. SR формулируй от потребности конкретных участников («Покупателю нужна…», «Сторонам нужна…»), не от действия решения («решение должно…» относится к FR). Если создание резерва и сохранение блокировки имеют разные проверяемые эффекты, отрази их отдельными FR. Сохрани условие удержания денег до выполнения согласованных условий, без предположений о договорной обязательности. Приём условий — отдельное действие FR; запрет раннего резервирования принадлежит условию FR резервирования, не добавляй его вторым действием в FR принятия. Отмена и истечение срока требуют отдельных SR и отдельных FR — они имеют независимо согласуемые исходы. Бизнес-правила отражай также в CTX при необходимости. CON создаётся только из закона, договора, стандарта или политики с подтверждённой обязательностью; определения терминов сами по себе не создают CON. Не добавляй реализацию неизвестного спора/неответа: подтверждённую потребность сохрани в SR, неизвестный механизм в GAP. Все явно названные условия сохраняются. Прежде чем вернуть JSON, проверь каждую строку и её GAP/родителя; не надейся на следующий проход.

Создание сервиса и описание его устройства — scope/CTX, не самостоятельная бизнес-цель BR. «Обеспечить расчёты, при которых деньги резервируются до исполнения условий» описывает решение, а не зачем оно организации: не создавай из этой фразы BR. Самостоятельный BR формулирует желаемый результат организации, например привлечение новых клиентов. Подтверждённое устройство сервиса остаётся SR/FR/CTX с исходными условиями. Не заменяй отсутствующий бизнес-результат названием сервиса или функцией; зафиксируй GAP при его отсутствии.
