# Исполнение оригинального BABOK-скилла в веб-приложении

Профиль `requirements-decomposition@2.3.0` использует оригинальный пакет
`babok-requirements-v3@1.0.0`. Методика не переписывается в отдельный промпт:
сервер собирает `SKILL.md`, три обязательных и четыре дополнительных reference-файла
целиком в system message. Загрузчик проверяет хеши каждого файла, а задача сохраняет
версии и manifest hashes пакетов скилла и промптов.

`server/src/skills/babok-execution.js` — адаптер исполнения и сериализации.
Он задаёт JSON вместо Markdown и JSON Schema с явными типами записей: enum —
одна строка, коллекции — массивы. Схема строится из деклараций контракта реестра
в `babok-wire-contract.js`. Модель возвращает содержательные поля и outcome;
materials, scope и summary.counts заполняет сервер. Правила классификации, атомарности, доказательности, выявления пробелов
и ответственности берутся из файлов скилла. Переданные документы находятся в
пользовательском сообщении и рассматриваются как данные.

## Проходы анализа

1. Декомпозиция единицы получает оригинальные инструкции, анализируемый фрагмент,
   полный исходный документ для проверки scope, baseline и справочники. Если
   фрагмент совпадает со всем документом, повторный текст не передаётся.
2. Глобальный проход получает те же оригинальные инструкции, **полный исходный
   документ**, baseline, справочники и черновики единиц. Он сверяет выводы с
   первоисточником, исправляет пропуски/классификацию, строит связи и DELTA, выполняет
   финальные проверки скилла и возвращает окончательный реестр.
3. Сервер проверяет структуру той же JSON Schema через Ajv, прежде чем обращаться
   к полям вложенных записей. Проверка собирает все нарушения формы; в repair
   передаются первые 50 с общим количеством, затем проверяются связи и инварианты
   реестра. Неизвестные поля сохраняются для совместимости со старыми конвертами. Машинно проверяемые правила качества скилла
   формируют замечания к черновику и не отклоняют весь ответ. В новом профиле
   он не удаляет требования, не угадывает происхождение, не склеивает записи по
   тексту и не удаляет неразрешённые ссылки. Допустимы приведение массива из одного допустимого enum-значения к строке
   (без выбора между несколькими статусами), перевод отсутствующего или пустого
   значения в null только для nullable-полей, заполнение серверных
   метаданных, подсчёт записей и явные GAP о недоступных дополнительных материалах.
4. При нарушении структурного контракта выполняется один repair-вызов с предыдущим ответом,
   списком структурных ошибок, исходными материалами и теми же system instructions.
   Если ответ повторно невозможно открыть как реестр, сервер сохраняет исходные
   ответы без изменений в `babok-text-draft.v1`. Такой результат доступен как
   текстовый черновик в вебе и через API (`format=raw` или `format=markdown`),
   с исходом PARTIAL. Редактор реестра для него недоступен. При отсутствии текста
   или техническом сбое модельного вызова результат всё ещё может отсутствовать.
   При временном сбое провайдера во время repair уже полученный ответ сохраняется
   с причиной сбоя. Отмена задачи, истечение общего дедлайна и неожиданные ошибки
   не маскируются. Причины нарушения сохраняются при объединении черновиков.
   Замечания к качеству не вызывают repair: их можно проверить в редакторе и отчёте.

В замечаниях к качеству проверяются, в частности: отсутствие предложенных требований
в подтверждённых groups, обязательные scope/verificationMethod для NFR, связь
статуса «Требует уточнения» с GAP, критерий завершения TR, роль готового SR,
покрытие BR/SR дочерними требованиями либо GAP, не более 7 вопросов и 5 выводов.
Замечания вычисляются по текущей редакции и исчезают после исправления. Они не
меняют требования, не придумывают недостающие GAP и не запрещают сохранение или
экспорт. Структурный контракт `babok-requirements.v1` сохранён. Строгий валидатор
качества остаётся доступен для квалификационных сценариев, но не блокирует рабочие задачи.

## Представление

Вкладка «Полный отчёт» использует тот же рендерер, что и Markdown-отчёт результата
задачи. Она сохраняет резюме и все 11 нумерованных разделов из `output-template.md`,
включая пустые. Качество отображает GAP-ID, трассировка сохраняет дополнительные
связи и предполагаемые отношения, baseline-ID не обязан быть ID нового реестра.
Таблицы прокручиваются горизонтально внутри контейнера. Редактор требований,
вопросов и сохранение версий остаются доступны рядом с отчётом.

## Проверка и воспроизведение

Локальные проверки:

```sh
node --test server/test/babok-skill-execution.test.js server/test/babok-wire-contract.test.js server/test/babok-report-renderer.test.js
npm -w client test -- src/BabokSkillReport.test.jsx
npm -w server run prompts:qualify
```

Реальный платный/квотируемый прогон через настроенный GLM-провайдер:

```sh
REQAI_E2E_MODEL=glm-5.3-flash node scripts/qualification/babok-skill-e2e.mjs
```

Скрипт использует только синтетические материалы из
`server/test/fixtures/babok-skill-scenario.json`, загружает baseline и справочник,
создаёт задачу с профилем 2.3.0 и проверяет все шесть типов требований, исключённый
scope, атомарность действий, NFR, GAP, независимые изменения baseline FR-901/FR-903,
модель исполнения и 12 разделов отчёта. `REQAI_BASE_URL` меняет адрес API;
`REQAI_E2E_EVIDENCE` сохраняет метрики и ID без содержимого документов и секретов.

## Границы эквивалентности

Это реализация ограниченного процесса исполнения данного скилла, а не универсальный
CLI-агент с файловыми инструментами. Все reference-файлы включаются заранее.
Модель, reasoning, температура и доступные материалы влияют на анализ; дословное
совпадение с CLI не гарантируется. Структура отчёта детерминирована, семантическую
эквивалентность проверяем по контрольным сценариям, а не по совпадению текста.

Полный источник намеренно не обрезается: это сохраняет межсекционные связи, но
требует, чтобы инструкции, материалы, черновики и ответ помещались в контекст
выбранной модели и лимит размера промпта. Максимальный размер загружаемого файла
не означает, что модель способна проанализировать весь этот объём. Превышение
лимита приводит к ошибке; скрытой выборки или заявления о полном охвате нет.
Проверка очень больших документов и широкое сравнение разных CLI-моделей остаются
отдельной квалификацией. Ошибки классификации естественного языка не устраняются
одним JSON-валидатором.

## Совместимость

Профили 1.0.0–2.2.0 оставлены доступными для сохранённых задач и отката.
Новые задачи по умолчанию выбирают 2.3.0. Для отката задайте
`PROMPT_DECOMPOSITION_ACTIVE_VERSION=2.2.0`, сохранив 2.3.0 в списке released,
пока существуют задачи с его snapshot. Оригинальный skill bundle не изменён.

## Передача контекста в исследование

Новые исследования используют `requirements-insights@2.1.0`. Модель получает
полный сохранённый реестр и основной документ, а также `decisions` выбранной
immutable-версии: ответы/состояния GAP, причины закрытия и замечания пользователя.
Дополнительно загружаются полные baseline и справочники из серверного
`materialLineage.sourceJobMaterials`. Baseline читается из канонического
`{status, artifacts}`; для старых сохранённых версий поддерживается массив.
Отсутствующий baseline (`NOT_PROVIDED`, `artifacts: []`) не мешает исследованию. Ссылки в редактируемом реестре сами по себе
не разрешают чтение других артефактов. Это одинаковый путь для веба, REST и MCP.

Если дополнительный материал недоступен, в запросе явно указывается `UNAVAILABLE`;
модель должна обозначить ограничение. Результат сохраняет статусы прочитанных
материалов в `researchMaterials`, исходные решения — в `baseDecisions`.
Для старой версии без серверного lineage дополнительные файлы не угадываются.
Тексты не обрезаются молча: превышение лимита промпта приводит к ошибке.

Профили исследования 1.0.0 и 2.0.0 сохранены для существующих задач. Новые
`reviewContext` и `supportingMaterials` объявлены в манифесте 2.1.0. Проверка:
`node --test server/test/requirements-insights-activity.test.js` — перехватывает
фактический запрос modelExecutor, проверяет передачу решений/материалов,
недоступный источник и совместимость старого профиля; внешний LLM не вызывается.


При ошибке или отмене исследования веб показывает «Повторить исследование».
Повторный запуск использует тот же ID сохранённой версии через доменную операцию
исследования и сохраняет связь с исходной декомпозицией. Двойное нажатие блокируется;
после неопределённого сетевого ответа повторяются те же тело запроса и ключ
идемпотентности, чтобы не создать два запуска. Новая декомпозиция не требуется.
