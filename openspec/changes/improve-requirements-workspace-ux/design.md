## Context

См. [proposal.md](proposal.md) и аудит. Это сквозное изменение: React-редактор, сохранённые версии, история и представление AI-результатов. Поэтому технический дизайн обязателен. Повторный live-аудит 31.08.2026 измерил proposal diff с колонками 31–39 CSS px на узком экране, overflow навигации типов на 25 px при desktop layout, 114 px высоты обёрнутой sticky-панели и контраст resting borders 1.20–1.78:1 при корректном focus indicator 7.9:1.

В `BabokRequirementCard` текст живёт в локальном состоянии размонтируемой карточки; `BabokRegistryResult` отдельно считает dirty-state реестра. `requirements-version-service.js` хранит immutable-артефакт с `registry`, `decisions`, `revision` и `baseVersionId`. В `decisions` уже находятся принятые/отклонённые enhancement keys. История использует job-ресурс; канонический URL — `/tasks/{jobId}`. Исследование привязано к сохранённой входной версии.

Главные specs пока отстают от реализованного BABOK change: местами описывают три категории вместо шести. Дельты этого пакета сохраняют реализованные BABOK-возможности и legacy-чтение. Перед будущим sync/archive надо согласовать порядок с `integrate-babok-requirements-skill`, а не применить старую дельту поверх нового UX.

## Goals / Non-Goals

**Goals:** одно определение несохранённых изменений; сервер — источник истины для сохранённых версий; независимые представления пользовательского документа и диагностики; небольшие проверяемые компоненты; аддитивные API-изменения; content-first композиция результата; читаемый responsive review; измеримый visual/accessibility baseline.

**Non-Goals:** новый task API или taskId, смена исследовательского провайдера, автоматическая загрузка внешних URL, CRDT/совместное редактирование, фоновое серверное автосохранение каждого нажатия клавиши, изменение immutable skill/prompt bundles, автоматическое исправление всех ошибок модели. Audit-hardening не перерабатывает research-карточки, их meter, evidence copy, фильтры, selected-state или sticky action bar.

## Decisions

### 1. Единое состояние редактора и явная граница сохранения

Выделить reducer/hook на уровне открытого реестра. Ключ контекста: авторизованный tenant/user, `sourceJobId`, базовая версия. Состояние содержит серверный snapshot, рабочий реестр, черновики полей по стабильным ID, review-решения, ошибки валидации и фазу сохранения. Карточка становится управляемым компонентом; смена типа/вида её данные не уничтожает.

`dirty` вычисляется по всему документу, включая ответы и AI-решения, а не только массивам требований. «Сохранить изменения» собирает и валидирует все черновики; невалидный черновик фокусируется, запрос не уходит. Локальное «Готово» закрывает редактор и НЕ означает сохранение на сервере. «Отмена» отменяет только текущую локальную сессию редактирования; общий сброс требует подтверждения.

Различать переход и сохранение: прямой переход к финалу из реестра требует чистой сохранённой версии. Кнопка «Сохранить финальную версию» на этапе исследования сама сохраняет выбранные решения и правки одной транзакцией после проверки и подтверждения открытых вопросов; dirty-state не должен создавать для неё тупик. До успешного ответа финальный этап не считается завершённым.

| Состояние | Сообщение | Допустимые действия |
| --- | --- | --- |
| Новый результат | Требования сформированы, ещё не сохранены | Редактировать, сохранить |
| Dirty | Есть несохранённые изменения | Сохранить, явно отменить; исследование/финал недоступны |
| Saving | Сохраняем… | Чтение; повторная отправка и изменение payload заблокированы |
| Saved | Сохранено, версия и время | Исследование или финал, редактирование, экспорт |
| Save error | Не удалось сохранить | Черновик остаётся, повторить после проверки результата запроса |
| Remote conflict | На сервере есть новая версия | Сравнить, загрузить с подтверждением; автоматической перезаписи нет |

Черновики сохраняются в `sessionStorage` текущей вкладки с версией формата и базовой версией, TTL 24 часа. Они удаляются при успешном сохранении, явном сбросе, смене аккаунта/выходе. Полные исходные документы, токены и ответы Debug туда не копируются. При недоступном хранилище остаётся память и явное предупреждение, что перезагрузка не сохранит черновик. В другой вкладке/устройстве восстанавливается только серверная версия. Восстановленный черновик никогда не показывается как сохранённый.

Альтернатива — сохранять каждый символ серверу — отвергнута: она смешивает черновик с проверенной версией, меняет API и порождает лишние ревизии.

### 2. Конфликты, повторные запросы и lineage

Для нового веб-клиента расширить `POST /api/v1/requirements/versions` необязательными `expectedLatestVersionId` (включая null для первой версии) и `clientMutationId`. Сравнение с последней версией source job и дедупликация выполняются атомарно под блокировкой; повтор mutation с тем же содержимым возвращает ту же версию, с другим — конфликт. Старые клиенты без полей продолжают существующий контракт. Не менять смысл `baseVersionId`: это непосредственная база документа; для первого исследовательского финала база — вход исследования, хотя последней версии child job ещё нет.

При событии SSE новая версия не вытесняет dirty-state. Показать сравнение по ID и полям; перенос своих изменений на новую базу выполняется только явным подтверждением, затем повторной валидацией. При неопределённом исходе сети повторять тот же mutation ID. Изменение документа после подтверждённой ошибки создаёт новый mutation ID.

Новые review-метаданные хранить в версионированном пространстве `decisions.review` (`schemaVersion: 1`): ответы и состояния GAP, подтверждение оставленных вопросов, отметка ручной проверки полноты и отредактированные AI-предложения. Существующие ключи решений и неизвестные совместимые поля сохранять при ревизиях. Сервер проверяет размеры, допустимые состояния, принадлежность record/insight IDs базе и формирует автора/время, не доверяя присланному actor.

### 3. Информационная архитектура и представление источников

Верх: название задачи, версия и единый save-status, затем четыре этапа. Рабочие разделы: «Требования», «Вопросы», «Связи». «Контекст и материалы» доступны по запросу; служебные детали только в Debug. Источник показывается как имя документа → раздел → цитата. При отсутствии имени используется «Исходный текст»/«Справочный материал», при недоступности — понятное предупреждение. Нельзя скрывать неполный охват вместе с диагностикой.

Режимы реестра: «По типам» фильтрует выбранный тип, «Все требования» показывает все типы, а выбор типа прокручивает и переводит фокус к секции. На узких экранах типы доступны через компактный выбор без скрытого горизонтального списка. Legacy три категории отображаются тем же подходом. Нулевые аналитические разделы свёрнуты, но доступны. Полезные BR/FR/GAP ID сохраняются и работают как ссылки.

Структурированный редактор раскрывается сбоку на широком экране и как полноширинный диалог на узком. Редактируются только поддерживаемые поля типа: роль, критерии, область, категория NFR, качество, связи. Источник/цитата исходного артефакта остаются read-only; ручное изменение помечается отдельно. Удаление показывает входящие связи, не оставляет dangling IDs и предлагает Undo до сохранения; ID не переиспользуется.

Сохраняем палитру и типографическую основу. Выделение компонентов — по состояниям и ответственности, без замены UI-стека. Альтернатива большого визуального переписывания увеличивает регрессионный риск без решения потери данных.

### 4. История без новой сущности задачи

Добавить nullable display title и revision метаданных к корневому decomposition job; child использует родительский title. Начальное название детерминированно из первой содержательной строки/имени файла (до 120 символов), без LLM-вызова. Для старых задач выполнить ограниченный по размеру пачки, возобновляемый backfill поисковых метаданных из доступного источника; иначе использовать локализованный тип + дату. До завершения индексации сообщать об ограничении поиска старых записей. Исходный immutable job snapshot не переписывать, пользовательские названия не заменять.

Аддитивные операции: `PATCH /api/v1/jobs/{jobId}/metadata` с проверкой revision, событие изменения метаданных; `GET /api/v1/jobs` получает необязательные `q` и `groupBy=workflow`. Группированный ответ сохраняет envelope пагинации, представляет root job и авторизованных детей, не вводит taskId. Поиск по сохранённому названию/краткому описанию работает на сервере по всему доступному набору; фильтр и cursor учитывают запрос. Не загружать полные артефакты для каждой строки истории. Для root, удалённого retention, доступный child остаётся самостоятельной строкой без утечки чужих метаданных.

Альтернатива client-only названий/поиска отвергнута: не переживает другой браузер и ищет лишь загруженную страницу.

### 5. GAP и полнота — решения пользователя, а не обещание модели

Исходный GAP неизменен как результат AI; ответ/статус review хранится в новой версии. Статусы: открыт, дан ответ, закрыт. Ответ сам по себе не закрывает GAP и не меняет требование: показать связанные записи, позволить изменить их и явно закрыть с причиной. Открытые вопросы не запрещают финал навсегда: перед финализацией пользователь подтверждает их список. Подтверждение связано с редакцией; изменение вопросов/ответов требует нового подтверждения.

Добавить режим сверки исходного текста и требований, отметку «Не проверено / Проверено пользователем» и возможность отметить пропуск/создать ручное требование. В тестовом брифе закрытие и открытие комнаты — два проверяемых обязательства. Не добавляем эвристику, которая выдаёт 100% полноты за совпадение слов. Детерминированные тесты моделируют пропуск открытия; реальный GLM-прогон отдельно фиксирует качество вывода без обещания одинакового ответа.

Отметка полноты привязана к содержимому источника и реестра; после их изменения прежняя проверка остаётся историческим свидетельством, а новая редакция требует повторной проверки.

### 6. Проверка AI-предложения и источников

Для каждого предложения показывать target type, связанные ID, исходный текст и редактируемую итоговую формулировку. Перед принятием показывать точную операцию: добавление или изменение одной явно выбранной записи. Текущие предложения по умолчанию добавляются; `targetIds` трактуются как связи, а не неявная команда overwrite. Для замены пользователь сам выбирает запись и подтверждает diff. При смене типа требуется заполнение обязательных полей.

Применение — чистая функция из базы, решений и overrides, проверяемая отдельно. Ключ предложения стабилен в пределах immutable research result. Повторное сохранение не создаёт дубликат. При отмене ранее принятого решения показывать diff, особенно если созданная запись вручную изменена: без явного подтверждения её нельзя удалить. База, оригинал предложения, final wording и resulting record IDs сохраняются в lineage. Не вырезать автоматически слова «Предложить уточнить»: пользователь подтверждает готовую формулировку, предупреждение помогает заметить инструкцию вместо требования.

Проценты сохраняем для совместимости, но подписываем «Оценка модели, не вероятность»; если обоснования нет, так и пишем. `source_types` — только тип материала, не доказательство. Поддержать необязательные структурированные источники: URL, title, publication date при наличии, кто/когда проверял. По умолчанию источник «Не проверен»; модель не может назначить ему статус проверенного. В этом пакете нет автоматического HTTP-загрузчика или нового research provider: пользователь может открыть безопасный HTTP(S) URL и отдельно зафиксировать ручную проверку. Старые результаты без ссылок честно показывают «Источники не предоставлены».

Защита вывода: безопасный Markdown/URL, отсутствие raw HTML и опасных схем. Смешанный язык выделяется как требующее проверки предупреждение без блокировки аббревиатур и цитат; исходный модельный текст сохраняется, принудительной скрытой перегенерации нет.

### 7. Экспорт только по versionId

Добавить авторизованный `GET /api/v1/requirements/versions/{versionId}/export?format=markdown|docx|html`. Общая модель документа строится из сохранённого artifact и review-метаданных, а не из текущего UI. Существующий Markdown job result endpoint остаётся без изменения смысла. Экспорт включает все типы, полезные ID, источники, открытые вопросы и решения; инфраструктурная диагностика исключена.

Markdown используется также для копирования; DOCX — через изолированную библиотеку генерации после проверки лицензии, без сетевых шрифтов/изображений. HTML имеет print styles для действия «Печать / PDF»: интерфейс честно открывает системную печать, а не обещает серверный PDF. Длинные таблицы/кириллица должны читаться без обрезки. При dirty-state предложить сохранить или явно экспортировать предыдущую сохранённую версию с её номером.

Альтернатива экспорта видимого DOM отвергнута: фильтры и несохранённые поля дают неполный/неверсионный документ. Серверный headless-browser для PDF сейчас не нужен.

### 8. Ввод, ожидание, фон и настройки

Свободный исходный текст фиксированной начальной высоты без шаблона или навязанной структуры; длинный текст прокручивается и не растягивает форму автоматически. Материалы по умолчанию скрыты под одним компактным действием с иконкой загрузки; после раскрытия раздельно обозначить основной материал, предыдущие требования и справочные документы. Использовать существующие integration material descriptors, ограничения загрузки и доступные нативные input.

Прогресс: подтверждённый этап из durable events + отдельно ориентировочное время. Таймер не придумывает выполняемую мыслительную операцию. Сбой сети отличается от сбоя задачи; retry/cancel сохраняют текущие серверные ограничения.

Создатель исследования переходит к child после ответа create. Другие вкладки и явно открытый parent показывают ссылку на child и остаются на выбранном URL; SSE не перехватывает маршрут. В фоне можно читать прошлые результаты или готовить контекст, но нельзя обходить лимит активных задач.

Настройки используют данные о возможностях модели от backend; если disabled фактически low, показывается «Минимальный», а не «Выключен». Отдельно доступны настройки следующего запуска и snapshot текущего результата. Перезагрузка сохраняет выбор следующего запуска в пользовательских настройках, но не меняет прошедший запуск.

### 9. Проверка и выпуск

P0 выпускается внутри ветки раньше остальных изменений. Вся ветка сливается только после согласованной приёмки. Для браузерных тестов worktree запускать на отдельных портах и с отдельной тестовой БД/томами; `.env` и секреты не копировать в git, текущий работающий стенд не останавливать и не мигрировать без явного решения.

Проверки: reducer/component Vitest, API/contract tests Node, MCP regression, build; браузерные состояния на 390/839/1440/1910 px и при 200% zoom, клавиатурные переходы и focus trap. Реальный сценарий переговорных повторить на GLM-5.3-flash low, включая сохранение, открытый GAP, отредактированное предложение и экспорт. Зафиксировать какие проверки детерминированны, а какие наблюдения относятся к одному запуску.

### 10. Audit-hardening вне research-карточек

Сохранённая финальная версия и review-реестр строятся content-first. На узком экране завершённый stepper сворачивается до компактного статуса текущего/завершённого этапа; настройки результата и экспорт остаются доступными, но не предшествуют основным review tabs, статусу версии и предупреждениям целым экраном. На широком экране сохраняется полный stage context. Sticky-области получают нижний reserve space и не закрывают сфокусированный контрол или первую содержательную карточку. Альтернатива — просто уменьшить все отступы — отвергнута: она снижает читаемость, не меняя неверный порядок внимания.

Proposal review использует два представления одной diff-модели. При достаточной ширине это три колонки с минимальной шириной labels/before и переносом длинного after; при недостаточной ширине каждая запись становится вертикальным блоком «Поле / Было / Станет». Заголовки и значения не переносятся по отдельным буквам, весь текст остаётся доступен, а footer actions достижимы внутри прокручиваемого диалога. Горизонтально прокручиваемая узкая таблица отвергнута: она заставляет сравнивать значения вне одного поля зрения.

Типы требований используют tabs только пока все полные подписи и counts помещаются без постоянного scrollbar; до возникновения overflow компонент переходит на доступный select. Breakpoint определяется вместимостью контента, а не предположением, что любой desktop шире фиксированного `lg`. Полные accessible names и keyboard semantics сохраняются в обоих режимах.

Визуальная основа остаётся indigo/slate, но presentation layer получает ограниченные роли вместо свободного сочетания utility-классов: один neutral family; semantic primary/success/warning/danger; пользовательская шкала 12/14/16/20/24/30 px, где 10–11 px остаются только для Debug; основные интервалы 4/8/12/16/24/32/48/64 px; не более трёх elevation levels. Static surface использует border либо subtle shadow, но не оба без функциональной причины. Resting boundaries необходимых input/select/button/tab достигают 3:1; normal text — 4.5:1; focus indicator — 3:1 и выше. Для сложных tinted surfaces используются явные tokens, а opacity сохраняется только для scrim/backdrop и анимационных overlay.

Автоматический title и контекстная выдержка становятся разными presentation fields. Генератор нормализует первую содержательную фразу, ограничивает автоматический title 64 символами по границе слова и не копирует в него весь brief; пользователь по-прежнему может сохранить валидное название до 120 символов. Header ограничивает display двумя строками, history показывает короткий title и отдельную одно-/двухстрочную выдержку. Для старых задач остаётся локализованный type/date fallback.

Research-карточки рассматриваются как внешний соседний surface: audit-hardening не меняет их grid, карточный текст, meter, evidence/disclaimer presentation, filter row, selection indication или sticky action. Общий proposal-review диалог меняется независимо и покрывается отдельными regression tests, чтобы последующий redesign карточек не был неявно включён в этот пакет.

## Risks / Trade-offs

- [Перекрытие старых OpenSpec changes] → перед sync сопоставить требования, сохранить новые правила маршрутизации и шесть BABOK-типов; не архивировать чужую незавершённую работу.
- [Расширение объёма] → P0/P1/P2 отдельными коммитами и тестами; не добавлять новый провайдер, автопоиск или новый дизайн-стек.
- [Черновик содержит рабочие данные] → session-only storage, TTL/очистка и ограничение объёма; не обещать долговременное или межустройственное восстановление.
- [Источник со ссылкой выглядит достоверным] → ссылка не равна проверке; статус проверки задаёт пользователь, а не LLM.
- [Старый клиент перезапишет review-поля] → сохранять совместимые неизвестные поля при серверной ревизии от базы, покрыть mixed-client тестами; не менять старые артефакты.
- [Группировка истории скрывает этапы] → раскрываемая цепочка и прямые ссылки на каждый job; авторизация каждого дочернего элемента.
- [Различия печати PDF в браузерах] → обещать печатное представление, проверить целевые браузеры; прямую выдачу PDF оставить отдельному будущему решению.
- [Токены могут превратиться в скрытый редизайн] → менять только роли, необходимые для измеримых hierarchy/contrast/spacing дефектов; бренд, DOM-семантика и research-карточки сохраняются.
- [Compact final header может скрыть важный статус] → оставлять этап, version/save state и coverage warning видимыми; убирать только повторяющиеся завершённые пояснения и вторичные disclosures из первичного порядка.

## Migration Plan

1. Проверить чистоту базы `4771717`, существующие тесты и пересечения OpenSpec. Добавлять только изменения этого пакета.
2. Внести аддитивные nullable поля/индексы метаданных и хранилище дедупликации сохранений; выполнить возобновляемое заполнение только поисковых метаданных старых задач, без изменения immutable artifacts.
3. Развернуть совместимый backend раньше UI, проверить старые API/MCP клиенты и доступность метаданных/экспорта.
4. Подключать UI по этапам; до готовности backend не показывать недействующие rename/search/export controls.
5. Выполнить тесты/реальный прогон, показать пользователю итог и только после одобрения объединить ветку с исходной.
6. Откат: вернуть frontend/backend к контрольной версии, сохранив новые артефакты и nullable данные. Старые версии должны читаться; новые review-метаданные старый UI может не показывать. Не выполнять destructive down-migration. Для повторного включения новых функций данные остаются доступными.
