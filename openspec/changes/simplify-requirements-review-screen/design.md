## Context

Основание: пользовательский скриншот от 10.09.2026 и исходники; live-поведение и геометрия браузера в рамках подготовки не измерялись. См. [proposal.md](proposal.md). `BabokRegistryResult` сейчас совмещает `layout`, `activeType`, разделы и фильтр уточнения; в режиме `columns` выбор типа прокручивает страницу, в `rows` фильтрует. Родитель отдельно выводит исходную задачу и баннер по одному `linkedChildId`. Галочка в шапке отражает наличие сохранённой версии, а не полноту.

Основные specs содержат старое описание трёх колонок; завершённые неархивированные changes добавили BABOK, сохранность и research split-view. Новая дельта заменяет два требования главной spec, уточняя этап 2; остальные гарантии предшествующих changes сохраняются. При последующем sync порядок: BABOK → workspace UX → linked research review → это изменение; не синхронизировать старое описание колонок поверх нового.

## Goals / Non-Goals

**Goals:** компактный экран работы с документом, явные независимые состояния, повторное использование существующих handlers и review-state, изоляция изменений этапом 2.

**Non-Goals:** новая модель workflow, переписывание редактора, новые запреты на финализацию, перенос research-review или изменение дизайна финального редактора. Не считать общее число GAP числом нерешённых GAP.

## Decisions

### 1. Один верхний блок и немедленный переход к содержимому

Сохранить текущие шрифт, indigo-акцент, нейтральные поверхности и стили полей. Убрать обрамление у структурной шапки, отдельную карточку исходной задачи и крупный баннер. Заголовок 24 px, обычный текст 14–16 px, метаданные 12–14 px; отступы 8/16/24 px служат исходными токенами, уточняются в существующей системе. Рамки оставить у интерактивных полей и содержательных карточек. По уточнению пользователя цветная верхняя полоса каждого блока типа сохраняется как ориентир: BR — синий, SR — голубой, FR — фиолетовый, NFR — янтарный, TR — оранжевый, CON — розовый. Компактная компоновка не отменяет эту маркировку. По дальнейшему уточнению пользователя формулировка требования занимает всю внутреннюю ширину карточки: отдельное ограничение max-width у текста удалено, общие отступы и выравнивание влево сохранены.

Каркас desktop (пример: сохранено, исследование завершено; без ошибок):

```text
Контекст ✓ ── Требования 2 ── AI-исследование 3 ── Финальная версия 4

Требования                         [Посмотреть результаты AI]
Сохранено · 11:19  Полнота: не проверена · Сверить
                                   К финальной версии   Экспорт ▾
Исходная задача: Обеспечить новый канал…   Посмотреть и изменить
AI-исследование завершено · для этой версии

Реестр · 3   Вопросы · 5   Связи   Полный отчёт

Тип: [Все типы ▾]   □ Нужно уточнить       + Добавить требование

Бизнес-требования · 1
BR-001   Формулировка требования…                         Изменить
…
Требования заинтересованных сторон · 2
…
```

Ссылка на исходную задачу открывает существующий просмотр/редактирование с защитой черновиков. Экспорт остаётся рядом с действиями и экспортирует ту же сохранённую версию. Раздел «Вопросы» сохраняет GAP и вопросы; счётчик вопросов остаётся только во вкладке, количество пробелов показывается внутри этого раздела. Отдельная строка счётчиков удалена. Сверка раскрывается рядом со статусом сохранения по запросу, сохраняя существующее содержимое `CompletenessReview`; в свернутом виде не занимает отдельную карточку.

Альтернатива — только уменьшить padding: отвергнута, поскольку оставляет дублирование и неоднозначную навигацию.

### 2. Приоритет действий вычислять из существующего состояния

Выделить небольшую presentation-модель для шапки, передавая из родителя linked job, статус и входную version ID. Не создавать второй источник истины: использовать текущие job/version загрузки и SSE. Если поля отсутствуют, получить детали через существующий read API либо показать неизвестное состояние; не выводить «выполняется» из наличия child ID.

Приоритет сверху вниз:

| Состояние | Основное действие | Остальные действия |
|---|---|---|
| Конфликт/ошибка валидации | Существующее действие разрешения проблемы | Переходы ограничены существующими guards |
| Нет версии / есть изменения | Сохранить требования / Сохранить изменения | Запуск и финализация недоступны; переход к child защищает черновик |
| Сохранение выполняется | Сохраняем… (disabled) | Защита от повторной отправки |
| Запуск исследования, ID ещё нет | Запускаем AI-исследование… (disabled) | Без повторного запуска |
| Исследование текущей версии активно | Открыть AI-исследование | Финализация недоступна по текущему guard |
| Исследование текущей версии завершено | Посмотреть результаты AI | Финализация вторична; «Запустить повторно» в дополнительных действиях |
| Нет исследования текущей версии | К финальной версии | «Улучшить с AI · необязательно» вторично |
| Исследование не удалось / отменено | К финальной версии, если разрешено | Открыть детали; повторить явно, если разрешено |

Если активно исследование старой версии, глобальный active-job guard имеет приоритет: не разрешать новый запуск/финализацию только из-за несовпадения версий; доступно открытие существующего child. Не менять cancellation, retry или admission semantics. Для завершённого/неизвестного состояния старой версии явно указать принадлежность, не подменять его вход текущим реестром. Если статус неизвестен, не ослаблять существующие launch/final guards.

Сохранение показывать нейтральным текстом; зелёная отметка допустима только рядом с точным статусом ручной проверки. Проверка имеет состояния «Полнота: не проверена», «Полнота: проверено вами», «Полнота: нужно перепроверить» по существующим metadata. Текст не обещает автоматической полноты.

Альтернатива — всегда показывать финализацию главной: отклонена для активного/готового исследования, поскольку скрывает уже начатую работу. AI остаётся необязательным, завершённое исследование не вводит новый gate.

### 3. Один фильтр вместо двух способов выбора типов

На этапе 2 использовать один labelled select «Тип требований» с «Все типы» по умолчанию и всеми поддерживаемыми типами с полным названием и количеством. Все типы показывают непустые группы в стабильном порядке BABOK; legacy использует свои категории. Выбранный пустой тип показывает пустое состояние и добавление. Общая кнопка добавления позволяет выбрать любой тип.

«Нужно уточнить» остаётся независимым фильтром по существующему правилу качества, не по GAP. При нулевом результате показать сброс фильтра. Смена фильтра и раздела сохраняет drafts. Навигация к ID снимает скрывающий фильтр, выбирает нужный раздел и фокусирует запись. Возврат между разделами сохраняет фильтр, новая задача начинает с «Все типы». Старый localStorage layout не удалять и не перезаписывать: он остаётся у этапа 4. Общие компоненты получают отдельный вариант этапа 2; read-only источник исследования не меняется.

Альтернатива — чипы шести длинных названий: возможны, но выбрана единая компактная форма, одинаково понятная на desktop и mobile.

### 4. Адаптивность и проверяемая геометрия

На 390 px: компактное обозначение текущего этапа с доступом к остальным, затем заголовок/сохранение, основное действие, вторичные действия с переносом, исходная задача, строка AI, разделы/сводка, фильтр и реестр. Не добавлять вторую sticky-панель. При 200% zoom применять reflow; не обрезать подписи и focus.

Приёмка по fixture из spec: 3 коротких требования (BR=1, SR=2), 5 GAP, 5 вопросов, clean saved version, связанное исследование, нет исключительных ошибок, все disclosures закрыты. Измерять от верха полного viewport, включая app header: desktop 1440×900 — начало первой записи не ниже 480 px и минимум две строки формулировки видимы; mobile 390×844 — ID и начало текста видимы без прокрутки. Это целевые критерии, не измерения текущего UI. Длинные тексты, ошибки, partial coverage и открытые disclosures могут увеличить высоту; существенные предупреждения не скрывать ради метрики. Для них проверять доступность и отсутствие overflow.

## Risks / Trade-offs

- Общие компоненты обслуживают несколько этапов → новый режим явно ограничить stage 2; регрессии проверить на финале и read-only источнике.
- Старые specs ещё не синхронизированы → перед archive сверить перекрывающиеся блоки, не терять сохранность, BABOK и lineage.
- Linked ID не содержит актуального статуса → использовать authoritative metadata, явно обрабатывать загрузку/недоступность и принадлежность версии.
- Сжатие может скрыть важные предупреждения → partial coverage и ошибки остаются видимыми; компактность проверяется отдельно на нормальном состоянии.
- Фильтр менее нагляден, чем шесть карточек → показывать название и количество в вариантах, сохранять добавление в пустые типы.

## Migration Plan

Изменения только frontend, без миграции данных или новых зависимостей. Сначала выделить модель состояния и stage-two presentation, затем подключить оба формата результата. Сохранить прежние storage keys и route handlers. Проверить матрицу состояний, frontend suite, lint/build и браузерную геометрию. Откат — возврат frontend-коммита, сохранённые версии и черновики совместимы.
