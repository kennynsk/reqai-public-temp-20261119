## Context

Мотивация — в proposal.md. Реестр BABOK и решения GAP уже объединены в клиентском черновике (`review-state.js`, `ReviewDraftProvider`). `ReviewQuestions` и `RequirementClarifications` обеспечивают ручной путь к редактору. Сохранение версии выполняет серверную валидацию. Есть адаптеры LLM, фоновые задачи, события, авторизация и аудит; диалог должен использовать этот контур, не вводя отдельные клиентские ключи провайдера.

## Goals / Non-Goals

**Goals:** отделить беседу, структурированное предложение и принятую правку; воспроизводить контекст каждого ответа; сохранить несохранённые пользовательские правки и версионную проверку.

**Non-Goals:** превращать сообщения в команды редактору, запускать полную декомпозицию на каждый ответ, автоматически считать GAP решённым. Для MVP редактируются только существующие требования; изменение связей, источников, ID, качества и решений GAP не входит в предложение AI.

## Decisions

### Контекстная панель

Кнопка «Обсудить с AI» у требования и GAP открывает одну панель с ID, названием, историей и полем сообщения. Переключение записи переключает диалог, а не переименовывает активную беседу. Черновик сообщения сохраняется отдельно для каждого диалога. На desktop панель расположена рядом с рабочей областью; на мобильном занимает доступный экран, имеет заголовок, закрытие, корректный фокус и возврат к инициатору. Открытие панели не отправляет запрос LLM. Глобальный плавающий чат отложен: он оставляет предмет разговора неявным.

### Снимок на каждый ход

Сервер принимает выбранную запись, baseVersionId и ограниченный клиентский снимок текущего черновика. До отправки клиент собирает незавершённые редакторы без потери текста; невалидные редакторы требуют исправления, а не молчаливого возврата к сохранённой версии. Сервер проверяет владение задачей/версией, допустимость ID, поля и размеры. Пользовательский черновик маркируется как несохранённый, а не как достоверный исходный документ.

Контекст: выбранная запись, непосредственно связанные требования, связанные GAP и ответы/решения, исходные цитаты и доступные фрагменты материала. При отправке из GAP все связанные требования включаются, если помещаются в бюджет. Не включаем скрыто весь архив задачи. Храним manifest включённых ID, версию, нормализованный hash снимка, сведения об исключённых материалах и время. При превышении бюджета сохраняем запись и вопрос, сокращаем историю/дополнительные материалы с явным уведомлением. Если обязательный контекст не помещается, просим сузить запрос. В MVP нет веб-поиска и автономных инструментов.

### История и API

Предлагаемые сущности: discussion (tenant, owner, job, anchorId), message (role, status, generationId, contextSnapshotId), context snapshot, proposal (target IDs, before, after, baseHash, status), acceptance receipt. Один диалог на anchor в задаче; версия фиксируется на каждом ходе, поэтому сохранение следующей версии не теряет историю. История и источники доступны только в пределах действующих прав на задачу. Удаление задачи удаляет историю по общей политике хранения.

API создания/чтения диалога, отправки сообщения с idempotency key, подписки на generation events, отмены генерации. Одна активная генерация на диалог; конфликт возвращается явно. Переиспользовать инфраструктуру LLM/событий после проверки её совместимости с короткими интерактивными запросами. История пагинируется. Завершённые сообщения неизменяемы; повтор ошибки создаёт отдельную попытку, не дублируя пользовательский ход. Отмена не гарантирует возврат расходов провайдера, но прекращает показ новых частей и блокирует предложения незавершённого ответа.

### Предложение как валидируемый пакет

LLM возвращает текст объяснения и необязательный пакет правок с существующими targetId, beforeHash, предложенными значениями и обоснованием. Разрешены text и предметные поля BR.successIndicator, SR.role, NFR.category/scope/verificationMethod, TR.completionCriterion, CON.obligation/scope. Сервер валидирует контракт, существование ID и список разрешённых полей; источники, provenance, quality, связи и закрытие GAP моделью не меняются. Принятая формулировка помечается существующим механизмом ручной проверки AI-предложения; исходная цитата сохраняется.

UI показывает сравнение всех полей и записей. MVP принимает или отклоняет пакет целиком: выбор отдельных зависимых правок отложен. Применение повторно сравнивает текущий собранный черновик с hash основания каждой записи и значениями связанных GAP-ответов. Если ответ или хотя бы одна целевая запись изменилась/удалена — пакет устарел, перезаписи нет; можно запросить новый вариант на свежем контексте. Нет автоматического слияния.

Применение — одна атомарная операция локального review reducer, вместе с маркером proposalId. Повторное применение не дублирует эффект. Это ещё не сохранённая версия. Общая кнопка сохранения передаёт receipt с proposalId и итоговыми изменениями, сервер проверяет полномочия и фиксирует происхождение в аудите. Состояния «принято в черновик» и «сохранено в версии» различаются; отмена/отбрасывание черновика снимает первое, не удаляя историю беседы. Принятие не закрывает GAP: используется независимое подтверждение ручного пути.

### Проверка всех требований одного GAP

В GAP и в уточнениях карточки отображается один общий список связанных требований с прогрессом «Проверено 1 из 2». Каждая пара gapId/requirementId имеет состояние pending, incorporated («Ответ учтён») или no-change («Изменение не требуется»). Для no-change обязательно краткое объяснение. Отметки пользователь ставит явно после применения редактирования; принятие AI-пакета не выставляет их автоматически. Список охватывает все связи GAP.affectedIds и обратные ссылки relatedIds/relatedTo на GAP, с устранением дублей. Неразрешённая ссылка показывается как проблема, а не исчезает из проверки.

Отметка хранится в review metadata, а не в тексте требования: статус, обоснование, hash ответа и формулировки GAP, hash проверенной записи; автор и время фиксируются сервером при сохранении. Изменение ответа или вопроса сбрасывает все отметки; изменение требования — отметку только этой записи. Добавление связи создаёт pending, удаление существующего требования оставляет блокирующую ссылку до явного исправления связи. Открытый редактор блокирует подтверждение соответствующей записи. При устаревании подтверждений уже решённый GAP возвращается в answered/open с объяснением; прежнее решение остаётся в истории. Проверки и сбросы выполняются также при серверном сохранении, а не только в интерфейсе.

Кнопка «Закрыть вопрос как решённый» доступна при непустом ответе и актуальных отметках всех связанных требований. GAP-002 с SR-003 и FR-005 можно закрыть после двух отметок, в том числе если одно требование изменено, а второе уже удовлетворяет ответу. GAP без связанных требований не считается решённым автоматически: остаётся отдельный путь решения с причиной. «Снять вопрос с рассмотрения…» сохраняется как явное исключение с обязательной причиной и отдельным closureKind=dismissed; оно не утверждает, что ответ учтён. closureKind=resolved обозначает закрытие по полной проверке. Старые закрытые GAP без этих данных остаются legacy, с пометкой «Закрыт ранее · проверка по требованиям не зафиксирована», без выдуманных отметок.

Проверка является частью ручного пути и работает при выключенном AI. Общая кнопка сохранения атомарно сохраняет требования, отметки и решение. Это расширяет текущий ручной интерфейс, где пока есть только общее подтверждение для всех требований.

### Политика генерации

Использовать текущую выбранную модель/настройки через серверную конфигурацию; сохранять их у попытки. Ограничить размер сообщения, контекста, ответа, число параллельных генераций и частоту запросов конфигурацией. Все материалы и сообщения — данные; инструкции в исходном документе не разрешают системные действия. Не исполнять HTML, команды или ссылки из ответа. Недостаток данных должен приводить к уточняющему вопросу, а не выдуманной метрике или цитате.

## Risks / Trade-offs

- Несохранённый текст меняется во время генерации → снимок и проверка основания перед применением, отказ от тихого слияния.
- Несколько связанных требований требуют согласованной правки → единый пакет и атомарное принятие.
- Перегруженный контекст и стоимость → ограниченный manifest, бюджет, отмена и отсутствие вызова при простом открытии панели.
- Ответ выглядит как подтверждённое требование → разделение беседы/предложения/версии, явное сравнение, без автоматического закрытия GAP.
- Потеря сети после принятия → локальный receipt в восстановлении черновика и идемпотентное сохранение.

## Migration Plan

1. Добавить таблицы и API аддитивно под флагом; существующие версии без discussion metadata валидны.
2. Подключить панель, сначала проверить диалог без принятия на фиксированных провайдерных фикстурах, затем включить предложения и receipts.
3. Проверить tenant isolation, восстановление, конфликт версий, мобильный UX и ручной путь без AI. Выполнить ограниченный живой прогон только в рамках явно разрешённого тестирования.
4. При откате выключить entry points/генерации; сохранить историю и уже принятые версии. Не удалять пользовательские данные миграцией отката.
